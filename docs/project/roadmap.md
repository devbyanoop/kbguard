**Status: met.** `kbguard scan` works end-to-end against all three stores — verified for real (not just in tests) with a real `kbguard scan` run against each. Docker runs on a different machine on the network, reached via `DOCKER_HOST=ssh://...`; the test suite's connection host is configurable via environment variables rather than assuming `localhost` (see [Contributing](../project/contributing.md)) specifically because of this.

Verified as a genuinely installed console script (`kbguard --help`, `kbguard scan --help`), not just through typer's test runner. 4 tests, lint-clean, strict-mypy-clean.
- [x] `examples/policy_corpus/` — 16-chunk synthetic demo corpus with planted problems (exact + near duplicate, a stale version pair that's also a numeric contradiction, an unrelated contradiction pair, four chunking-damage cases, three clean chunks). Verified against a real Qdrant container the same way as pgvector.

## Checks, health score, first report

**Goal:** every seeded problem in the example corpus is found; first HTML report renders.

- [x] `checks/base.py` — the `Check` Protocol + `CheckContext` (config + optional live adapter/collection for checks needing a self-retrieval probe; no `judge` field yet — added when `judge/client.py` exists and `contradictions.py` actually needs it). Plus `registry.py` gained a `checks` entry-point group (`load_check`, `list_available("checks")`) — the mechanism that keeps `faiss`/`datasketch` honestly optional: confirmed by hand that importing the registry or an adapter pulls in neither, only `load_check("duplicates")` does.
- [x] `checks/duplicates.py` — exact (normalized-text hash) + near (`faiss` cosine ANN candidates, confirmed only with `datasketch` word-set Jaccard) duplicate detection, union-find clustering for transitive chains, severity escalated to `error` across sources. Verified against the real example corpus: finds exactly the two planted duplicate pairs, nothing else. Found and fixed a real bug in the original architecture spec along the way: the default `minhash_jaccard: 0.9` was measured against real paraphrased text and would almost never fire — corrected to `0.3` (see `docs/guide/checks/duplicates.md` for the full comparison table). `SnapshotReader` gained a bulk `vectors()` accessor (deferred earlier specifically until this real caller needed it). `hnswlib` (originally planned as an ANN option) can't build on Windows without MSVC Build Tools — used `faiss-cpu` instead, which ships a working prebuilt wheel. Also closed a real gap found earlier: `tests/test_plugin_registration.py` only ever tested Chroma's registration, never pgvector/Qdrant — fixed.
- [x] `checks/stale_versions.py` — groups by `title` (falling back to a normalized source/filename stem), orders by `updated_at` (falling back to `version` string), flags every member but the newest, escalates to `error` via a self-retrieval probe (query the *live* store with the stale chunk's own embedding, check if the current version also comes back in the top 5). Verified against the real example corpus and a live Chroma connection: the planted pair is found and genuinely escalates, confirmed by a real search call, not assumed.
- [x] `checks/chunking_damage.py` — six deterministic rules (`size`, `split_table`, `orphan_heading`, `broken_sentence`, `missing_metadata`, `encoding_noise`), no embeddings/LLM/optional deps. Verified against the real example corpus: added a missing planted example (`encoding-noise-1`, control characters in payment-methods text — the corpus had no example for that rule until this review caught it) and fixed a real bug found by hand: `pricing-table-cut`'s cut-off last row (`"| Pro | $25/mo"`) was passing every heading heuristic and getting double-flagged as `orphan_heading` in addition to the correct `split_table` finding, fixed by excluding any line containing `|` from the heading check. Also found the corpus's chunks (3-25 words, built for easy hand-verification) all sit under the spec's global `min_tokens: 40` default — not a spec bug, so fixed with a corpus-local override (`examples/policy_corpus/kbguard.yaml`) rather than changing the global default. 24 tests including a real-corpus integration test asserting the exact rule-to-chunk mapping.
- [x] `judge/client.py` + `judge/cache.py` — provider-neutral `JudgeClient.ask_json()` via `litellm`'s model-string routing (verified `response_format={"type": "json_object"}` is a parameter litellm actually maps for `ollama/*` models too, not just hosted APIs — checked with `litellm.get_supported_openai_params`, not assumed), JSON parsing with exactly one retry on malformed output (`JudgeError` after 2 failed attempts, never a silent `None`), responses cached by a `sha256` request hash in a `JudgeCache` sqlite file living inside the snapshot's own directory. `litellm` imported lazily inside the one method that makes a real call, not at module level — a `JudgeClient` can be constructed, and even hit its cache, with `litellm` never installed. Caught and corrected an overclaim already written into `docs/guide/evals/judge-and-calibration.md` before this file existed ("re-scanning unchanged data costs zero new LLM calls") — the cache is scoped to one snapshot, and `cli.py`'s `scan` command writes a new, differently-named snapshot directory every run, so a second scan always starts with a cold cache; what it actually buys is free re-runs of checks/report/diff against the *same* already-written snapshot. 14 tests (fake `litellm` module via `sys.modules`, same technique as `ingest/embeddings.py`'s tests — no real network call, no dependency on the extra being installed).
- [x] `checks/contradictions.py` — clusters chunks by plain-numpy cosine similarity (0.6, well below duplicates' 0.97 — a looser "same topic" grouping, not near-duplicate detection; measured against the real corpus's two genuine pairs at 0.7071/0.6402 vs. its highest unrelated pair at 0.5432), extracts facts via 5 priority-ordered regex patterns (money/percent/duration/date/number, each claiming its span so a more specific type's digits never double up as a bare `number` fact — including when that type is disabled, a real bug found by a test that assumed otherwise), finds each fact's subject via `spaCy`'s `en_core_web_sm` noun-chunk head-lemma (verified by hand against both real planted pairs before trusting the design), pairs same-subject/different-value/*confirmed*-different-source facts, and sends only those candidates to the judge. `CheckContext` gained its deferred `judge` field (typed as a new `JudgeLike` Protocol, not the concrete `JudgeClient`, so a lightweight fake judge works in tests the same way `_FakeSearchAdapter` already does for adapters). Verified against the real example corpus: exactly 1 of 17 chunks' worth of facts ever reaches the judge (`warranty-a`/`warranty-b`) — `return-window-v1`/`v2` is same-subject/different-value too, but shares one source (different version, same doc), correctly left to `stale_versions` instead of being double-flagged. Found during integration, not in isolation: `enabled` defaulting to `true` would've broken every existing scan with no judge configured, since this is the one check that genuinely can't run without one — fixed by flipping its default to `false`, matching this project's own "judge-dependent features stay off until configured" principle. 11 tests plus a real-corpus integration test.

Found and fixed a real, independent bug while building this: the original spec's `pinecone-client>=4.0` dependency is deprecated — installing and importing it now raises its own exception telling you to install `pinecone` instead, confirmed by actually installing it, not assumed from memory. `pyproject.toml` fixed to depend on `pinecone>=5.0`. ## Evals, judge, diff, CI

**Goal:** a chunking change shows up as a failing `diff`.

- [x] `evals/golden.py` — `generate(snapshot, n, judge) -> pd.DataFrame` samples up to `n` chunks (deterministic seed, so re-running against an unchanged snapshot samples the same ones) and asks the judge to write one specific, answerable question per chunk — the first use of the judge for *generation*, not yes/no classification. `approved` is always `false` in the output; `freeze(csv_path, out_path)` filters to approved rows and assigns each a stable `id = sha256(question)[:16]`. Found and fixed a real bug while testing against a realistic half-reviewed CSV, not a clean one: a human leaving even one row's `approved` cell blank makes `pandas` infer that column as mixed type (`bool`/`NaN`), and a naive boolean mask on it raises `ValueError: Cannot mask with non-boolean array containing NA/NaN values` — confirmed by hand. Fixed by parsing each cell explicitly instead of trusting pandas' automatic dtype inference. `pandas>=2.0` added as a core dependency, `pandas-stubs` to `dev` for `mypy --strict`. 13 tests including a real-corpus simulation of a human approving 2 of 5 generated rows and leaving the rest blank.
- [x] `evals/retrieval.py` — `evaluate_retrieval(golden, adapter, collection, snapshot, k_values, embedder) -> list[EvalResult]`: hit@k/recall@k/precision@k/MRR@k/nDCG@k, one `EvalResult` per (question, metric, k). Formulas derived by hand on two toy examples first (per the plan's own advice) before coding — asserted against full floating-point precision (e.g. `ndcg@3 = 0.6309297535714574`), not "roughly reasonable." Cause tagging reads the content checks' own findings directly: `content` if an expected chunk is missing or already flagged, `retrieval` if it exists and is unflagged but wasn't surfaced, `none` if it passed — the concrete link that makes "trace every failure to a cause" real. 12 tests including a real-corpus case (a chunk's own embedding used as the query finds itself).
- [x] `evals/target.py` — `RagTarget` calls a client's Python callable (`importlib`, `module:function`) or HTTP endpoint, normalizing either a `(answer, contexts)` tuple or a `{"answer":..., "contexts":...}` dict into the same shape. Every failure mode (client exception, HTTP error, timeout, a response that doesn't match `answer_path`/`contexts_path`) raises one `RagTargetError`, confirmed `httpx.HTTPError` is the real common base for timeouts/status errors/connection errors before relying on that in the `except` clause. JSON-path extraction is a deliberately limited dotted-only subset (`$.field.nested`), per spec's own "don't pull in a full JSONPath library unless you need wildcards." `TargetConfig` gained a `timeout` field (HTTP only — no cross-platform-safe timeout exists for a plain Python call without real threading complexity). 17 tests via `httpx.MockTransport` (real httpx, no real network) and a fake Python module.
- [x] `evals/metrics/base.py` — the `Metric` Protocol (`score(question, answer, contexts, reference, judge) -> EvalResult`), pure interface per the plan's own verify-by.
- [x] `evals/metrics/ragas_plugin.py` — wraps `ragas` 0.4.x's `Faithfulness`/`AnswerRelevancy`/`ContextPrecisionWithoutReference`/`ContextRecall` directly. Found and fixed a real packaging bug installing it: `ragas`'s own `langchain-community` dependency is unconstrained, and pip resolving the latest (0.4.x) breaks `ragas` outright — `ragas.llms.base` imports a `langchain_community.chat_models.vertexai` module that no longer exists there. Fixed by pinning `langchain-community<0.4` in the `ragas` extra. ragas's LLM wrapper needs `instructor.from_litellm()` (structured-output/tool-calling, not a plain prompt) — verified by hand up to the real-provider-call boundary (construction never hits the network; scoring does, and genuinely can't be exercised further without a real provider, since `litellm`'s `mock_response` returns plain text and `instructor`'s mode needs an actual tool call). Also found `ragas`'s own `embedding_factory()` silently defaults to an OpenAI embeddings client regardless of the configured judge model — fixed by wrapping kbguard's own configured embedder into a tiny `BaseRagasEmbedding` adapter instead, verified working for real (no network) before use. 10 tests against an injectable fake ragas metric object, the same "fake the library's entry point, not its internals" principle as everywhere else in this project.
- [x] `evals/metrics/deepeval_plugin.py` — wraps `deepeval`'s `FaithfulnessMetric`/`AnswerRelevancyMetric`/`ContextualPrecisionMetric`/`ContextualRecallMetric`. `DeepEvalBaseLLM` turned out much simpler than ragas's wrapper (plain text in, plain text out, no tool-calling) — confirmed by actually scoring a real `FaithfulnessMetric` with a mocked `litellm` response: it reached deepeval's own internal schema validation and failed only because the mock content didn't match deepeval's specific multi-step schema, never on a wiring error, meaning this LLM wrapper is genuinely unit-tested end to end, unlike ragas's. `deepeval.*` added to `mypy`'s `follow_imports = "skip"` override list (incomplete type stubs, same treatment as `sentence_transformers`/`litellm`/`datasketch`); `sklearn.*` added with plain `ignore_missing_imports` (no stubs, but not heavy/crash-prone enough to need the stronger treatment). 13 tests.
- [x] `judge/calibrate.py` — `calibrate(labels_path, judge, out_path) -> CalibrationResult`: plain agreement + Cohen's kappa via `sklearn.metrics.cohen_kappa_score` (a library implementation, not hand-rolled). Verified by hand: identical label lists score 1.0, full disagreement scores 0.0. Found a real edge case by hand: when every label (human and judge) is identical, kappa is mathematically undefined (0/0) and `sklearn`'s own default returns `NaN` — fixed by passing `replace_undefined_by=0.0` explicitly, confirmed this really does return `0.0`, never `NaN`, before trusting it. 8 tests.
- [x] `scoring/diff.py` — `diff_snapshots(baseline, current, fail_on, suppressions, weights, baseline_eval_results, current_eval_results) -> tuple[DiffResult, int]`. New/resolved findings via a plain fingerprint set difference; health delta via the same `compute_health`/`summarize_findings` pair the health score already built; metric deltas as mean-value differences per metric name. `DiffResult` gained a `suppressed_fingerprints` field beyond the plan's literal shape sketch, specifically because the spec's own design note requires suppressed findings to stay visible in `new_findings`, not vanish — this field is how a caller tells which ones were suppressed without mutating the shared `Finding` model. `load_suppressions()` reads `kbguard.ignore.yaml` (flat mapping keyed by fingerprint). 17 tests including the plan's own exact verify-by: a hand-constructed new error finding with `fail_on.new_findings.max: 0` returns exit code 1; suppressing that fingerprint flips it to 0 while it's still listed.
- [x] `cli.py` (third pass) — `golden generate`/`golden freeze`, `calibrate`, `eval`, `diff`. `eval` always runs retrieval metrics (no judge needed) and additionally runs configured answer-quality metrics (gated by a passing calibration) if `evals.metrics`/`judge`/`target` are all set; one broken question's target call is reported as a failed result, never a crash. Metric plugins (`ragas.*`/`deepeval.*`) are resolved by name and imported lazily, only when actually requested — `kbguard scan` (the common case) never pays for ragas/deepeval's genuinely heavy dependency trees. 12 CLI-level tests covering the full golden→calibrate→eval→diff pipeline, including real bugs found while testing: a toy-embedding test fixture dimension mismatch against `get_embedder`'s real `sentence-transformers` default, and snapshot-id timestamp collisions / a real Chroma `InternalError` from re-adding to an already-persisted collection in-process (worked around by constructing the second snapshot directly rather than via a flaky second live rescan).
- [x] `.github/workflows/kbguard.yml` — kbguard's own CI: pgvector/Qdrant as real GitHub Actions service containers (host port 5434 matching this repo's own default, no extra env vars needed), ruff, mypy --strict, pytest, mkdocs build --strict, across Python 3.10 and 3.12. Kept deliberately separate from `examples/ci/kbguard-client-template.yml` — the copy-pasteable template a client runs kbguard against *their own* KB with, explicitly marked with `TODO`s for what only they can fill in (extras, credentials, how to carry a baseline snapshot id between CI runs).
- [x] **Goal check** — met: a hand-constructed new `error`-severity finding shows up as a failing `kbguard diff` (exit code 1), verified via a real CLI invocation end to end, not just a unit test of the underlying function.
- [x] **Real-API hardening pass** — every judge-dependent test up to this point had used a fake judge or a fake `litellm`/vector-store module; this pass re-verified the judge-dependent paths against a real Groq account end to end and found three more real bugs no fake could have caught: (1) `judge/client.py` never set `temperature`, so the same exact prompt to the same real model returned different verdicts across calls (confirmed by hand, 3 calls, 3 outcomes) — fixed with `temperature=0.0`; that alone wasn't sufficient, since `groq/openai/gpt-oss-120b` then *deterministically* misjudged the suite's own planted contradiction while `groq/qwen/qwen3.8-27b` deterministically got it right, a real model-capability gap rather than noise.
